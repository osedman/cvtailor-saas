# End-to-end test — Tailr for Agencies on staging, 23 September 2026

Head under test: `f4dca2e` (staging, after the brief build). Database:
`tailr-staging`. Five testers worked in parallel, each on one slice, against
the REAL staging schema and data: recruiter loop (create → close), the
hiring-manager surface, the token doorways + email + crons + purge, the new
client brief, and a performance/schema audit. No browser session was
available (magic-link sign-in), so the method was:

- every write path probed as `service_role` inside blocks that always roll

- lib functions run directly against staging data with fake contexts built

- every route traced end to end for the request/response contract.

Every finding below was either verified by effect or by a trace naming the
line. "Fixed" means fixed in this session's commit; "needs a migration" means
Ose runs SQL first; "needs a decision" means it is Ose's call.

## The one Ose reported: "I can't remove client access even if they're in"

**Cause.** The Client access page loaded its rows once and never again. A
contact who accepted the invite while the tab sat open still showed
"Invited · Revoke invite". Revoking then correctly failed on the server
("invite already accepted — unlink the contact to remove access"), the
optimistic update rolled back to the STALE row, and the "Remove access"
button never appeared. The database allowed the unlink the whole time
(probed, 1 row, rolled back); Supabase's logs show no PATCH to
`client_contacts` ever left the app; no `unlinked` audit row has ever been
written. It was a refresh away.

**Also true, and worth knowing:** both linked contacts on staging (Ose,
Yemi) are ALSO active recruiters in Halcyon. Removing their CLIENT access
leaves their recruiter login untouched — so "they're still in" would be
correct even after a successful removal.

**Fixed.** The page re-reads on focus/visibility and after any failed
action, so the row offers the act that is now right. Rows say "Also a
recruiter here — removing client access leaves that login", and the confirm
names Settings → Team as the place to suspend that. Archived contacts leave
the list.

### MEDIUM — not fixed, listed for Ose

- **Re-parsing a JD** upserts `R01…Rn` by index: recruiter-edited requirements are overwritten and reset to `origin: parsed`; longer earlier parses leave orphan `R(n+1)…` with evidence bound to text that changed; no rescore follows. Needs a design (versioned requirements or a confirm that names what will be lost).
- **`saveIntake` is fire-and-forget** (`page.tsx:576`): a 403 (viewer), a rejected contact or "nothing to update" all render as saved. Same at `cycleWeight` and `removeRequirement`.
- **"Sent to the client" is claimed for document/email formats** that send nothing; the pane advances the phase and the resend dialog says it emails. `next-action.ts` gets it right.
- **Superseded evidence quotes travel to the client as "strong"** (submission builder ignores evidence layers; `rescore.ts` does not). Up to five quotes about one requirement.
- **Consent ask leaves no UI trace**; pressing it again mints a new hash and kills the candidate's first link.
- **No server gate on round decisions**: a decision on a future or cancelled round, or before any write-up, is accepted; only the UI gates.
- **Two definitions of "my role"** on the HM side (`decision-completions.ts`, `/hiring/roles/[id]/brief`) — scoped by `role.contact_id` only, so a recipient-only contact loses the "That's all my decisions" band and the brief chip.
- **Brief-connect card** does not refetch when the company is typed after load; company matched by exact string ("Meridian" ≠ "Meridian Ltd").
- **Failed loads still read as empty** in: close-out role/candidates fetch, close-out contacts, `SentLinks`, interviews page slots/candidates, `/hiring` briefs fetch, `getBriefForClient` / `listBriefsForClient` on DB error, `client_actions` read in the shortlist mapper (which also makes the already-acted guard fail open → duplicate actions).
- **Reference request/remove take `referenceId` from the body** and ignore the candidate in the URL (same tenant only).
- **Notice cron**: 50/day with no ordering by `scheduled_for`; a backlog can push an Art 14 notice past the 28-day cap. Transcriptions drain 2/day, scans 3/day.
- **`/booking` is not in `APP_PATH_PREFIXES`**; on the split hosts it is served wherever it lands.
- **`GET /api/hiring/roles/[id]/brief`** distinguishes "no such role" from "not your role" — an existence oracle every other route avoids.
- **`current_version` vs `max(version)`** can drift under two concurrent amends → unique violation surfaced as 500.
- **`discardDraft`** — fixed to 404 on an unknown brief.

## Performance

The per-call latency is ~20–50ms since the `dub1` pin. What remains is the
NUMBER of sequential calls per click. Counted by tracing each handler at a
realistic load (10 candidates, 2 rounds each, 3 recipients, 5 briefs):

| Route | calls | sequential depth | worst offender | fix |
|---|---|---|---|---|
| `POST …/submission` | ~105 | ~25 | `buildEntry` per candidate → `recomputeAndStore` → `loadScoringState` (6 calls) + serial recipient loop | Batch-load candidates/evidence/reviews/breakdowns with `.in()`, score in memory, one bulk upsert (→ ~7) |
| HM room click | ~80 | 10 | The index page mounts `useHiringData` to compute a redirect, then the stage page mounts it again: 2× `/today` + 2× `/dashboard` + `/brief` | Resolve the stage server-side, or lift `useHiringData` to `app/hiring/layout.tsx` |
| Close-out screen | ~74 | ~10 | Nine independent fetches; `getRoleFactsBatch` runs twice | One `/close-out` endpoint (→ ~25) |
| `GET …/roles/[id]/brief` | ~48 | ~23 | `listBriefsForCompany` calls `loadBrief` in a serial loop, 6 calls each | One `.in("brief_id")` read from the list rows (→ ~8) |
| `GET …/candidates` | ~31 | 10 | `getStagesForRoles` drags the 18-call facts batch into a list endpoint; **unbounded agency-wide `select *` on `score_breakdowns` and `candidate_evidence` with no `.eq()` at all** | Lightweight stage reader; scope the two selects to the role |
| `GET /api/hiring/today` | 26 (44 with 2 agencies) | 10 (16) | `for … of byAgency` awaits `getRoleFactsBatch` per agency | `Promise.all` |
| `GET /api/hiring/dashboard` | 13 | 10 | Five independent reads awaited one after another | `Promise.all` (→ 6) |
| `POST …/candidates` (ingest) | ~22 | ~20 | Serial chain | Parallelise pre-AI reads and post-AI writes |
| `GET …/header` | 22 | 9 | `getRoleFactsBatch`: six serial waves, paid by every role screen | One SQL view/RPC `agency.role_facts(role_ids)` |
| Interviews screen | 7 + N | — | `<InterviewCapture>` per round fetches on mount even inside a closed `<details>` | Fetch on open |

Also: `requireAgencyContext` / `requireHiringContext` are 3 sequential calls
each (getUser → members → agencies) — ~60–100ms before any route does work.
`listOpenSlots` reads every live slot in the agency and filters by role in
JS. `releaseDueWaves` loops up to 300 roles with `await` inside.

Client side: `RoleRow` defined inside render in `/hiring/roles` (remounts
every 60s tick); `useHiringData` `load()` has no abort/cleanup; the brief
page pays `/today` + `/dashboard` for a loading flag; two effects both call
`loadMatched()` on the role page; ten `loadReviewDetail` requests fan out on
entering screening.

## Checked and fine (so the reader knows what was covered)

- Every `/api/hiring/**` route scopes by the caller's own contact ids; a fabricated link and a wrong-agency link return nothing everywhere (run, not read). `forClient` strips agency/contact/role ids.
- The CV route: scoped to the submission not the ref; `disclosure.cv` reads OFF for both staging snapshots (they predate the key); `redacted` re-checked live; the audit row is awaited before the JSON is built; **0 `cv_viewed_by_client` rows — the route has never served a CV on staging.**
- The shortlist mapper: blanks `fullName` when redacted, gates every field on the frozen switches, reads actions across all of this contact's recipient rows.
- All 39 tables have RLS on, `force_rls` off; `member_agency_ids()`/`has_role()` are `SECURITY DEFINER` with `search_path` set — no recursion. `service_role` holds writes on all 39 (the August three-table defect is not present). `anon` holds nothing.
- Every CHECK constraint in `agency` read back: none dodgeable by NULL; the five iff-style ones all `coalesce`. Types in `lib/agency/types.ts` match the deployed checks — no drift.
- `sendEmail` refuses off-allow-list BEFORE the network call in non-production; every caller treats `{sent:false}` as not sent; closure, notices and references stamp only on `sent`.
- `notify.ts`: `facesClient` is a whitelist of four; client-facing kinds skip the recruiter's preference filter; the actor is never told about their own action; all five brief kinds have copy, a recipient and a CTA to a page that exists.
- Portal / reference / consent / booking / HM invite: sha256 only lands; malformed and cross-agency tokens 404 identically; replay refused where a token is spent; purged candidates cascade so their tokens die. `/consent` deliberately never spends its link (a decision may change).
- Waves role-scoped since 21 Sep; re-run same day → `wave_still_running`; per-role try/catch. Reminders, waves and scan sweeps each wrapped.
- Retention: role close stamps `retention_expires_at` by trigger; `purge_expired` collects recording paths before the cascade. New columns (`cv_text`, `references_wanted`, `kind`) die with the row; `brief_config` holds terms only.
- Brief: approved = both signatures on one row; amend inserts and never nulls a signature; connect requires approved, refuses company mismatch, writes all four columns at once; `signed_means_sent` and `brief_connection_whole` refuse in every direction (probed, rolled back).
- Round numbers derived; cancelled-row reuse; the partial unique index on `slot_id` is the double-booking mechanism; cancel frees the slot.
- Staging state now: 0 notices due (13 scheduled), 0 purge due, 0 scheduled rounds, 3 live portal links, 0 live reference/invite links, 0 redacted, 0 orphaned snapshot refs.
